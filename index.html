Operating workflow

Every coding task follows a small number of durable invariants.

1. Bind the workspace

Identify the device, repository root, branch, HEAD, remotes, and dirty state before editing.

2. Preserve user work

Pre-existing changes are user-owned. Never reset, clean, overwrite, or silently absorb them.

3. Read before edit

Inspect the exact target, make the smallest necessary change, re-read it, then review the diff.

4. Validate in layers

Start with the cheapest falsifying check. Escalate only when the task warrants broader proof.

5. Bound the evidence

Keep large logs on the host. Return summaries, failed items, relevant tracebacks, and compact diffs.

6. Finish from live state

Re-check Git, changed paths, validation, and active processes before declaring completion or handing off.

Windows shell policy

Shell choice is infrastructure state, not conversational memory.

Use the live RDC default

defaultShell = pwsh.exe

# ordinary calls
start_process(command="...")

# avoid replaying old chat state
# shell="powershell"

Know the distinction

  • powershell.exe = Windows PowerShell 5.1
  • pwsh.exe = PowerShell 7+
  • Unexpected mojibake or profile behavior → verify live shell facts first.

Long-running jobs

The process is durable evidence. A chat timeout is not proof that the process failed.

< 60 seconds

Wait normally. Keep output bounded.

~1–3 minutes

Observe sparingly. Avoid repeated progress reads.

> 3 minutes

Launch once, retain PID + command + workspace, report RUNNING, then yield the chat turn.

Do not restart a long command because the page stopped updating, a tool call timed out, or ChatGPT stream recovery failed. Reconcile the original PID first.

Concurrent ChatGPT sessions

One RDC device is one shared machine runtime, not a set of per-chat sandboxes.

Shared across chats

  • Active process/session registry
  • Recent tool history
  • Filesystem contents
  • Git working trees and index
  • RDC configuration

PID-scoped, but ownership matters

stdout/stderr stays with the PID. However, a PID is not automatically “owned” by the chat that sees it in list_sessions.

Only interact with a process launched by this chat, or explicitly handed off as PID + command + workspace.

Shared read cursor

For active processes, read_process_output(offset=0) advances a shared lastReadIndex. With multiple readers, prefer a negative tail offset or an explicit absolute offset.

# safer for multiple readers
read_process_output(pid=1234, offset=-80)

# avoid unless there is exactly one reader
read_process_output(pid=1234, offset=0)
Never let two ChatGPT conversations write concurrently to the same Git working tree. For real parallel coding, use separate Git worktrees or separate checkouts.

Recovery and handoff

Every new conversation should reconcile current machine facts instead of trusting stale chat state.

Recover in this order

  1. Known PID/session
  2. Durable log or test report
  3. Git/filesystem effects
  4. Remote CI state

Troubleshooting

Common symptoms and the first discriminating check.

ChatGPT says “stream recovery polling timed out”

This is a ChatGPT Web turn/stream symptom. It does not prove that the Windows process stopped. Reconnect through RDC and inspect the known PID/session once.

A long test is still running after the assistant stopped replying

That is expected. The process is running on the Windows host. Resume using the same PID rather than launching the same command again.

PowerShell output contains mojibake

Verify $PSVersionTable, process executable, $PROFILE, and RDC's live defaultShell. Do not diagnose repository encoding until shell identity is confirmed.

Another chat sees my test PID

RDC session discovery is device-global. Visibility does not imply ownership. Match PID, command, workspace, and handoff evidence before reading or interacting with it.
