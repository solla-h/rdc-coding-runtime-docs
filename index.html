Operating contract

The runtime does not try to replace your development environment. It makes ChatGPT behave like a careful operator inside the one you already trust.

Bind the workspace

Identify the device, repository root, branch, HEAD, remotes, and dirty state before changing code.

Preserve user work

Pre-existing changes are user-owned. Never reset, clean, overwrite, or silently absorb them for convenience.

Read before edit

Inspect the exact target, make the smallest justified change, re-read the result, then inspect the diff.

Keep one execution owner

For long-running, expensive, or effectful work, retain the same device, workspace, command/target, and PID/session until the outcome is settled. Timeout or silence does not authorize a duplicate run.

Validate in layers

Start with the cheapest check that can falsify the change. Expand only when broader evidence is warranted.

Bound the evidence

Keep large logs on the host. Bring back exit state, failed items, relevant traceback windows, and compact diffs.

Route locally, execute centrally

When local capability choice is unclear, ask the read-only how-to-use advisor. ChatGPT remains responsible for the decision and performs the real action through RDC.

Finish from live facts

Re-check Git state, changed paths, validation, and active processes before declaring completion or writing a handoff.

Local capability routing without loading the whole machine into context

MACHINE_CONTEXT.md stays concise. Detailed CLI, Skill, and provider knowledge is loaded only when the current task actually needs it.

Machine hints stay small; local evidence stays local

  • ~/.rdc/MACHINE_CONTEXT.md records durable host facts and capability hints, not full manuals or schemas.
  • how-to-use receives a bounded task capsule and asks an isolated local Pi runtime which capability fits.
  • User Pi Skills are referenced from ~/.pi/agent/skills; Pi's shared ~/.agents/skills source remains available without copying Skill bodies.
  • The advisor is read-only. The primary ChatGPT agent keeps control of every repository edit, deployment, Git operation, or external mutation.

The router is advisory, not autonomous. It exists to resolve local capability uncertainty without turning a second coding Agent loose on the machine.

First run is a bootstrap, not a manual installation guide

The bootstrap Skill installs the local advisor runtime, opens one configuration file for the user, validates the chosen model, then records a healthy runtime state.

{
  "api": "anthropic-messages",
  "baseUrl": "https://api.example.com",
  "apiKey": "replace-with-your-api-key",
  "model": "claude-sonnet-4-6",
  "thinking": "medium"
}

One user-edited file

  1. Bootstrap installs the versioned how-to-use runtime under ~/.rdc/how-to-use.
  2. It opens config.json in the local editor. The user fills in API protocol, Base URL, API key, model ID, and thinking level.
  3. how-to-use --verify-config performs a real inference check.
  4. how-to-use --benchmark verifies basic inference, Skill routing, and multi-tool/schema reasoning.

pi-agent/models.json and settings.json are generated runtime files. The user-facing source of truth remains ~/.rdc/how-to-use/config.json.

Shell is infrastructure state

RDC's live defaultShell is the source of truth. Old chat history must never silently choose the next shell.

defaultShell = pwsh.exe

# ordinary command
start_process(command="...")

# do not inherit this from old chats
# shell="powershell"

Know what the names mean

  • powershell.exe means Windows PowerShell 5.1.
  • pwsh.exe means PowerShell 7+.
  • Mojibake, an unexpected profile, or shell-specific behavior should trigger shell verification before repository debugging.

Execution keeps one owner

A process or mutation can outlive a tool call, a chat turn, or a stalled browser stream. Keep one authoritative owner until the outcome is settled; the UI is not that owner.

< 60 sec

Wait normally

Keep output bounded and return the real exit state.

~1–3 min

Observe sparingly

Use at most a small number of targeted reads. Do not turn progress into a polling loop.

> 3 min

Launch once, then yield

Record PID, command, workspace, and durable log path when practical. Resume the same process later.

Do not duplicate unresolved work because ChatGPT stopped updating, a tool call timed out, or transport failed. Reconcile the original PID/session or mutation target first; unresolved effectful work remains OUTCOME_UNKNOWN.

One RDC device is a shared machine

Multiple ChatGPT pages can use the same Windows host, but they do not receive isolated sandboxes. Ownership has to be explicit.

Ownership rule

Only interact with a process this chat launched, or one explicitly handed off with PID + command + workspace and reconciled against live state.

Active processes share one lastReadIndex when readers use offset=0. Multiple readers should use a negative tail or an explicit absolute offset.

# safer when multiple readers may inspect the PID
read_process_output(pid=1234, offset=-80)

# avoid unless the process has exactly one reader
read_process_output(pid=1234, offset=0)
Never run two coding chats against the same Git working tree. Use separate Git worktrees or separate checkouts for real parallel development.

Recovery starts with evidence

A new conversation should reconcile current machine facts instead of inheriting stale branch, shell, process, or dirty-state assumptions.

  1. Known PID or session identity
  2. Durable log or test report
  3. Git and filesystem effects
  4. Remote CI state

Troubleshooting by first discriminating check

Symptoms can look similar across ChatGPT Web, RDC, PowerShell, and the underlying process. Verify the layer before acting.

Why does pi-agent/models.json not show my thinking level?

~/.rdc/how-to-use/config.json is the user configuration source. The runtime generates models.json for provider/model metadata and writes the selected thinking level to pi-agent/settings.json and the Pi invocation.

Why is pi-agent/auth.json just {}?

That is normal for a custom router provider whose API key comes from the generated models.json. auth.json is Pi's isolated login store and can remain empty when no Pi-native login flow is used.

ChatGPT says “stream recovery polling timed out”

This is a ChatGPT Web turn/stream symptom. It does not prove the Windows process stopped or failed. Reconnect through RDC and reconcile the known PID/session or target state before any retry.

A long test is still running after the assistant stopped replying

That is expected. The process is running on the Windows host. Resume the same PID instead of launching the command again.

PowerShell output contains mojibake

Verify $PSVersionTable, the process executable, $PROFILE, and RDC's live defaultShell. Do not blame repository encoding before confirming the shell.

Another chat can see my test PID

RDC session discovery is device-global. Visibility does not imply ownership. Match PID, command, workspace, and handoff evidence before reading or interacting with it.

Version history

The plugin evolves from observed failure modes in real RDC coding sessions. Runtime rules change only when the behavior is understood and reproducible.

0.6.3
Execution ownership + outcome reconciliation

Generalizes the proven advisor PID-ownership rule to long-running, expensive, and effectful work. Unknown outcomes stay unknown until reconciled; no generic Job runtime, checkpoint database, or second Agent Loop is added.

0.6.2
Exclusive advisor PID ownership

Adds the immediate wait_for_pid=true ownership marker and prevents duplicate capability investigation while the native Pi advisor is still running.

0.6.1
Native Pi Agent Loop restored

Removes the outer semantic router, two-pass LLM orchestration, and thin production fallback while retaining deterministic read-only capability evidence.

0.4.0
Bootstrap + dedicated local capability router

Adds the first-run bootstrap Skill, versioned local advisor installation, isolated Pi router configuration, shared Skill sources, explicit model/thinking configuration, and runtime verification/benchmarking.

0.3.1
Single router configuration source

config.json becomes the user-facing source of truth for API protocol, Base URL, API key, model, and thinking level. Pi remains primary with a thin compatibility fallback.

0.3.0
how-to-use local capability advisor

Adds bounded local capability routing with machine context, lazy Skill discovery, isolated local reasoning, and primary-Agent execution control.

0.2.0
Durable machine context

Adds ~/.rdc/MACHINE_CONTEXT.md bootstrap/refresh rules so host-specific capability knowledge persists without becoming a giant tool inventory.

0.1.4
Documentation link

The plugin now points its homepage and ChatGPT website link to this documentation site. Runtime behavior is unchanged.

0.1.3
Concurrent RDC session safety

PID ownership, device-global tool history awareness, shared read-cursor protection, Git working-tree concurrency rules, and worktree guidance.

0.1.2
Long-running job protocol

Launch once, retain PID, stop active polling, yield the turn, then resume the same process when the user returns.

0.1.1
Windows shell hardening

Use live defaultShell as source of truth, distinguish PowerShell 5.1 from PowerShell 7+, and stop inheriting stale shell arguments.

0.1.0
Initial runtime contract

Workspace safety, Git baseline protection, bounded evidence, validation, recovery, and resumable handoffs.

RDC Coding Runtime is the policy, machine-context, capability-routing, execution-ownership, and workflow layer. Remote Desktop Commander remains the execution transport.
